## 2. 网络泛化实验：v8 / v8c（MuJoCo 闭环）

### v8：单一共享相位网络 + 共享 token 解码器（负面结果）

设计：`phase net: (proprio 930, cmd 14) -> (sin phi, cos phi)`（单一 MLP 覆盖全部
14 组）+ `token dec: (sin phi, cos phi, cmd 14) -> 64-d token`。

结果（`outputs/distill_v8/`）：
- 共享相位网络 val MSE 0.243（sin/cos 域），**per-group 相位角误差 0.85–2.29 rad**；
  对比 v6 per-group 相位 MLP 的 ~0.001–0.016 rad，退化了约 100–1000 倍。
- token 解码器 val MSE 0.00078（给定准确相位时可重构 token）。
- **结论：proprio→phase 映射强分组相关，池化到单一网络会破坏相位预测；
  相位阶段必须保留 per-group 结构。**（与「每命令组一个路由器」的经验一致）

### v8c：per-group 相位网络 + 单一共享 token 解码器（替代 40-bin 原型）

设计：相位仍由 v6 per-group MLP 预测（~0.005 rad 精度）；token 由单一解码器
`(sin phi, cos phi, cmd 14, frame one-hot 14) -> 64-d` 生成。unseen 命令走
fallback 组相位帧 + unseen cmd 输入解码器，连续插值而非离散跳组。

结果：token 解码器 val MSE 0.00076。闭环评测见第 4 节。

## 4. 闭环对比结果（v6 vs v8 vs v8c，待填）

评测脚本：`eval_battery_v8.py`（MuJoCo 无带闭环，与 eval_battery_v6 同口径：
20s × 3 seeds；unseen 场景含 slow@0.35 与 walk 的 6 个缺失 bin 方向）。

### 结果摘要（结果 JSON：`outputs/distill_v8/eval_battery_v8.json`）

| 场景 | v6（原型 fallback） | v8（共享相位网） | v8c（共享解码器） |
|---|---|---|---|
| walk_fwd | 3/3，16.9m | 0/3（~5s 倒） | **3/3，16.3m** |
| walk_back | 3/3，-16m | 0/3 | **0/3（~3.5s 倒，vx≈0）** |
| slow_fwd / slow_back / idle | 3/3 | slow_back 2/3 | 3/3（slow_back 位移降为 0.17m） |
| jump | 3/3 | 2/3 | 2/3 |
| turn_right | 3/3 | 0/3 | 0/3（437–554 步倒） |
| turn_left | 3/3 | 0/3 | 3/3 |
| strafe_right | 3/3 | 1/3 | 0/3 |
| strafe_left | 3/3 | 1/3 | 3/3（几乎不动） |
| stealth | 0/3（教师上限） | 0/3 | 0/3（略长于 v6） |
| **slow_speed35（unseen）** | 3/3（fallback 行为） | 3/3 | 3/3 |
| **walk_bin5/7（unseen）** | 3/3（走成前进） | 0–2/3 | **bin5 3/3、bin7 2/3** |
| **walk_bin1/2/3/6（unseen）** | 3/3（走成前进） | 0–2/3 | **0/3** |

### 结论（数据/网络泛化）

1. **v8 是明确负面结果**：把 14 组的 proprio→phase 回归池化进一个网络后，相位
   误差从 ~0.005 rad 恶化到 1.6–2.3 rad，闭环全场景失败。proprio→phase 映射
   强分组相关，不能简单共享。
2. **v8c 部分成功但总体不优于 v6**：相位准确时共享解码器在 walk_fwd 与 v6 持平，
   但 walk_back/turn/strafe/unseen-bin 更差。原因：连续解码器输出的 token 不是
   训练流形上的精确点，闭环误差累积（与 BC 回归失败的机制同源）；v6 的离散原型
   + fallback 反而在闭环中更稳——fallback 至少把命令「降级」成已学过的稳定步态。
3. **对用户问题的直接回答**：
   - 数据侧：unseen 命令（walk 的 6 个缺失 bin、连续速度）需要补数据；插值/降级
     无法创造新行为（v6 会把斜向命令走成前进，方向错误但安全）。
   - 网络侧：需要的是**带正则的结构化潜空间**（论文 TVAE / Gaitor 的连续 gait
     latent），而不是朴素条件回归——v8/v8c 证明了普通回归解码器会离开训练流形。
     若继续走网络泛化路线，下一步是真正的 VAE 式解码器（KL 正则 + 重建），
     与论文 TVAE 对齐，而非更大的条件 MLP。
4. 顺带发现：**倒走对 token 扰动更敏感**（v8c walk_back 0/3 vs walk_fwd 3/3），
   倒走是后续任何连续/潜空间方案的更严测试项。

## 5. 数据侧实验：exp3 补采 walk 方向 + v9 重建（2026-08-12）

### 补采（drive_exp3.py，官方闭环，0 次跌倒）

- 用 planner 键盘驱动：mode 2 + 周期性 q/e（heading ±π/6/次）做左右旋转扫描，
  加上 strafe（,.）与 slow 速度增减（9/0）。

  walk bin1=705 / bin2=1200 / bin3=623 / bin5=705 / bin6=1499 / bin7=558，
  另有 slow speed 0.6（1002 步）。

  base64 内容），exp2_raw 未受影响，exp3 数据已复制到 `data/exp3_raw/`。

### v9 重建与闭环评测（train_phase_router_v9.py + eval_battery_v9.py）

| 场景 | v9 结果 | 对比 |
|---|---|---|
| walk_fwd | 3/3，16.9m | = v6 |
| walk_back | 3/3，vx −0.56..−0.73，11.9–15m | 略慢于 v6（−0.78，16m） |
| idle / slow_back / turn / strafe | 3/3 | = v6 |

### 教师上限检查（oracle_walk_bins.py）：官方 token 直接回放

walk 全部 6 个新方向 bin 的官方 token 回放都在 **95–270 步内跌倒**：
bin1=216、bin2=270、bin3=144、bin5=95、bin6=177、bin7=137。

**结论（数据/网络泛化的完整答案）**：
1. 补数据把组覆盖补全了（v9 每个方向都有路由器），但闭环稳定性没有因此突破——
   瓶颈是 SONIC token 流形 + 本 MuJoCo env 的 walk+turn 稳定性上限（教师本身
   不行），不是路由器覆盖不足。
2. v9 在 bin5 把斜向命令"降级"成前进行走（3/3 稳定），在 bin3/7 比 oracle 多活
   2–4 倍——**降级到稳定步态是比直接执行教师不稳定行为更优的泛化**。
3. 因此对"是否需要更好的数据"：数据覆盖是必要条件但不是充分条件；真正决定
   泛化上限的是 token/解码器流形是否包含该行为（本实验里不包含）。
4. 网络侧：连续回归解码器（v8c）会离开流形；离散原型 + fallback（v6/v9）更稳；
   要超越上限需换数据/解码器（如带力矩标注的 TO 数据 + 力矩解码器，即论文
   原方案），或换环境（Isaac 的 G1 可能对 walk+turn 更宽容——待验证）。

## 7. TVAE-lite：论文表示学习阶段的直接实现（2026-08-12）

### 设计

`train_vae_lite.py`：encoder (proprio 930, cmd 14) -> z∈ℝ16；decoder (z, cmd) ->
64-d token；loss = 重建 MSE + β·KL(z‖N(0,I))，β 0→0.1 退火（防后验坍缩）。
这是论文 TVAE 的最直接类比（MLP 版）。

### 训练结果（exp_all3，68,093 步）

- **KL 后验坍缩**：β 退火后 val_kl → 0（z 被正则压成先验，信息归零）；最终模型
  val_rec 0.0088（远差于 v8c 的 0.00076）——高容量 cmd 条件解码器可以基本
  忽略 z 重建均值 token，相位变化作为小残差被 KL 杀掉。
- 最佳 checkpoint（β 小时保存，z 仍活跃）val_rec 0.000754。

### 闭环评测（最佳 checkpoint，z-EMA 0.3，20s×3 seeds）

| 场景 | 结果 | v6 对照 |
|---|---|---|
| idle | 3/3（站） | 3/3 |
| slow_fwd | 1/3（seed0 站住，其余 451–493 步倒） | 2–3/3 |
| slow_back | 0/3（685–819 步倒） | 3/3 |
| **walk_fwd** | **0/3（200–251 步倒）** | **3/3，16.9m** |
| walk_back | 0/3（258–499 步倒） | 3/3 |
| jump / turn_left / strafe_left / stealth | 0/3 | 3/3（stealth 教师上限） |
| turn_right / strafe_right | 3/3（但 vx≈0 站住） | 3/3 |

### 结论（网络泛化的完整证据链）

1. 三种"更好的网络"全部失败：共享相位回归（v8）、显式相位+共享回归解码器
   （v8c）、VAE-lite 学习潜空间（本实验）。失败机制：朴素回归/低正则解码器
   离开 token 流形（闭环误差累积）；KL 正则导致后验坍缩（相位信息被压掉）。
2. 现有最优结构仍是 v6/v9：**显式 PCA 相位 + 离散原型查表**——原型是训练流形
   上的精确点，闭环不漂移；相位是单值可回归信号，不像 token 那样多值。
3. 论文 TVAE 之所以有效，是因为 (a) 解码器输出**力矩**（PD 稳定，容忍小幅
   latent 误差），(b) TO 数据的物理结构让潜空间干净。我们的 SONIC 位置 token
   解码器 + 多值标签不满足这两个条件——这不是"我们没做对"，而是替代管道
   的固有上限。

## 8. 开源实现实证（unitree_rl_mjlab 源码核对，2026-08-12）

从 `https://github.com/unitreerobotics/unitree_rl_mjlab`（Apache-2.0）核对
G1 velocity tracking 的官方配方：

- **地形感知**：`RayCastSensorCfg` 生成 yaw 对齐的 1.6×1.0m 高度扫描网格
  （resolution 0.1m，max_distance 5.0m），作为 `height_scan` 观测直接进
  actor 与 critic——这正是论文/用户记忆里"先给地图"的主流做法；我们 E16 的
  9×9@0.15m 局部 elevation patch 方向一致但更小更粗。
- **显式 phase 观测**：观测含 `phase`（period 0.6s）——与我们的"相位路由器"
  用显式相位编码步态周期在思想上一致，进一步支持"相位是单值关键信号"。
- **奖励**：pose（站立/行走/跑步分档 std）、body_orientation_l2、body_ang_vel、
  foot_clearance、foot_slip、self_collisions 等丰富 task+style 项；我们只有
  5 项最小奖励（track_xy/yaw/upright/height/stillness），E17 的 idle 坍缩正是
  缺"必须前进"任务压力的直接后果。
- **并行**：默认 `--env.scene.num-envs=4096`；我们 RTX 3060 只能 64 envs。
- **命令**：lin_vel_x (-0.5, 1.0)、lin_vel_y (-0.5, 0.5)、ang_vel_z (-0.5, 0.5)，
  与我们训练 vx∈[0,0.8] 相比覆盖更宽（含负向与横移）。

**对照结论**：主流 G1 速度 RL 配方 = 地形高度扫描进策略 + 显式 phase + 丰富
奖励 + 千级并行。我们逐项复现了地形感知（E16）与相位（v6/v9），但奖励与并行
规模不足，且动作通道受限（aux-only / 离散 gate）——E15–E18 的负面结果与
官方配方逐条对应，说明差异在工程条件而非机制理解。

## 9. MuJoCo 本地粗糙地形（hfield）鲁棒性曲线（2026-08-12 夜）

目标：在 MuJoCo 平台上把"先验粗糙地形盲走"的曲线也补出来，与 Isaac 的
0.04/0.06/0.08/0.10 曲线对照。产出 `outputs/rough_mujoco_sweep.json`、
`rough_v9.mp4` / `rough_v6.mp4`（重渲染）。

### 9.1 MuJoCo 3.11 hfield 两个坑（已修复，`make_rough_xml.py`）

1. `elevation` 属性是**内联数字列表**，不是文件名；二进制地形要用
   `file="xxx.bin"` + MuJoCo 二进制格式（int32 nrow/ncol 头 + float32 数据）。
2. `size=(x, y, z, base_z)` 的 base_z 必须为正，而且 **base_z 不参与碰撞**：
   碰撞面 = `geom.pos.z + size[2] * data`。所以 geom pos z 必须设成 hmin
   （修复前机器人直接穿地，ncon=0，0.36s 内"蹲塌"——早期"0.06 立即全倒"是伪结果）。

### 9.2 地形生成（与 Isaac 的差异）

- 40×40m @0.1m 分辨率，0.4m 粗格均匀 ±amp，σ=1.2 高斯平滑，中心 0.4×0.4m
  铺平（出生点）。**没有坡度上限**，所以同一标称振幅比 Isaac 的
  HfRandomUniformTerrainCfg（slope_threshold=0.75）更陡。
- 坡度统计（seed 0）：

### 9.4 结论

1. **MuJoCo 本地地形阈值 ≈ 0.02–0.03**（v9：0.02 3/3 → 0.03 2/3 → 0.04 0/3），
   Isaac 同标称是 0.04 3/3、0.06 3/3。按坡度对齐（本地 0.02–0.03 的 p99≈0.08–0.12，
   与 Isaac 0.06 相当）后两者阈值一致——差异来自地形生成参数（无坡度上限），
   不是控制器或平台能力问题。
2. 失败模式：不是立即倒，而是先以 0.8–0.9 m/s 走出 3–5m，然后在小凸起/下陷上
   绊倒（h_min≈0.2）。这与 Isaac 的失败模式一致（先走一段再倒）。
3. idle（零 token）在平地就缓慢漂移并在 ~17–19s 绊倒；粗糙地形更早。
   **零 token 不是真正的驻留控制器**，只适合当"站住"的弱基线。
4. v6/v9 在 0.00–0.03 几乎无差异；0.06 上各有一次完整完成（seed 方差大），
   说明现有路由器在边缘地形上的稳定性主要被 seed 抖动支配。

### 9.5 平台对照闭合：平滑地形（coarse 1.0m、σ=3.0）复测

把本地 hfield 生成参数从"0.4m 粗格、σ=1.2"改为"1.0m 粗格、σ=3.0"
（amp 0.06 的 p99 坡度 0.10、max 8.6°，接近 Isaac 的 HfRandomUniform），
重测 v9 walk：

| amp | 陡地形（0.4/1.2） | **平滑地形（1.0/3.0）** | Isaac |
|---|---|---|---|
| 0.06 | 0/3（3.4–4.3m） | **3/3 完成（14.5–17.0m，vx 0.73–0.85）** | 3/3（38–43m） |
| 0.08 | 0/3（3.1–3.8m） | 0/3（4.1–10.2m） | 1/3（19–42s） |

**结论（平台差异闭合）**：MuJoCo 本地地形在坡度对齐后重现 Isaac 的阈值

## 10. 力矩级解码器实验（论文混合控制 tau = tau_dec + PD(q_default + aux)）

这是对论文"力矩级解码器 + 辅助动作"机制最直接的一次替代实现尝试。

### 10.1 力矩标签恢复（`recover_torque_data.py`）

- exp_all3（68,093 步 command/proprio/token）→ 离线重算 PD 力矩
  `tau = kp*(q_des−q) − kd*q̇`（前 12 个 MuJoCo 序下肢关节；q_des 由冻结
  SONIC 解码器从 token 解码）。按命令组抽样 14,633 行覆盖 19 组。
- 产出 `data/torque_data/`（input=[v9 相位 sin/cos + cmd14]、tau、norm 统计、
  group_ids、q_des）。ONNX 固定 batch=1，只能逐行解码。

### 10.2 解码器训练（`train_torque_decoder.py`）

- MLP 16→512→512→12（GELU+Dropout），输入 [相位, cmd]，输出归一化力矩。
- val RMSE 18.76 N·m（≈预测零的水平），per-joint MAE 1.9–29.2 N·m。
- 解释：**闭环 PD 力矩主要由瞬时跟踪误差 (q_des−q) 决定，相位+命令只能预测
  其周期均值**；这个 RMSE 就是不可约的反馈分量，不是拟合失败。

### 10.3 MuJoCo 闭环评测（`eval_torque_paper.py`，1000 步 × 3 seeds）

| 控制方案 | 平坦 walk | 粗糙 0.06 walk |
|---|---|---|
| baseline（token 位置路径） | 3/3，15.8–16.0m | 0/3（199–251 步，3.4–4.3m） |
| 论文式（tau_dec + PD(q_default)，aux=0） | **3/3 存活 20s 但 vx≈0.03（站住不前进）** | 62–82 步倒（1.2–1.6s） |
| 混合（token PD + tau_dec 前馈） | 63–73 步倒（1.3–1.5s） | 67–74 步倒（1.3–1.5s） |

### 10.4 结论：PD 力矩标签路线是死路，论文 TO 力矩不可替代

1. 纯论文式：解码器前馈 + PD(默认位姿) 能**稳住不倒**，但产生不了行走——
   步态的位置模式来自 token q_des 路径；相位条件均值力矩缺乏规划性（没有
   触地反力/摆动时序的"计划"成分）。
2. 混合式：把反馈力矩当正向力矩叠加 = 双倍反馈，直接失稳。
3. 因此，**从闭环 PD 力矩恢复"力矩先验"在原理上不成立**；要复现论文的
   aux 正向价值，需要真正的轨迹优化（TO）或逆动力学生成的前馈力矩数据，
   而不是记录 PD 力矩。这解释了我们 E2–E20c 所有 aux 负面结果的共同根源：
   替代管道里"力矩通道"这一层缺失且无法用 PD 标签廉价补上。

## 18. E25：相位锚定 + 消融（2026-08-13，方向 B 关键转折）

E24 的慢步态根因是自由相位学不会步态时钟。E25 把相位改为：
`phase = normalize(冻结 PhaseNet 时钟 + 0.15 × 策略偏移)`，时钟由 proprio
历史推进（与冻结路由器同源），策略只做有界调制；奖励沿用 E24（anti-stop

## 22. E27：latent→VAE→冻结 SONIC 解码器（无行为先验，2026-08-13）

用户指出缺失的实验：**自主学习（不用相位路由器行为先验），但运动仍经过
冻结 SONIC 解码器**。实现（复用论文 TVAE 结构 + 既往经验）：

- 相位条件化 token VAE：因果窗口（10×64）→ z∈ℝ16；D(z, sinφ, cosφ)→token。
  φ = walk mode-2 token 的 2-PC PCA 圆相位；时钟速率 0.121 rad/步（实测）；
  val recon MAE 0.079（无相位版 0.105，相位条件化更优）。
- Isaac latent 模式：策略每步输出 z，固定时钟推进 φ，D(z,φ)→token→冻结
  SONIC 解码器→关节目标。无路由器、无 aux。
- latent warm-start 200 iters → z_walk；奖励 = 速度跟踪 + anti-stop +
  progress；64 envs × 800 iters。

评测（A/B/C/D × 3 seeds）：

| 测试 | E27（latent，无行为先验） | E1 冻结先验 | E9/E11 vanilla（无 Sonic） |
|---|---|---|---|
| A 60s | 3/3，vx 0.32，**19.1m** | 3/3，47m | **0/3 立即倒** |
| B 500N | **12/12**（h_min 0.74–0.76） | 12/12 | - |
| C 68s 切换 | **3/3**（disp 19.7–19.8m） | 3/3 | - |
| D 跳跃 | 3/3（vx 0.34） | 3/3（vx 0.68） | - |

**结论**：
1. "不通过 Sonic 学习、但让 Sonic 动"是可行的：token 流形 + 相位时钟 +
   z_walk 初始化让 64 envs 从零 RL 学会稳定行走（E9/E11 直出关节 0/3 立即
   倒）。**Sonic token 流形本身是关键先验**。
2. 速度 0.32 m/s 未压满（先验 0.8）：z 收敛到慢速技能区，B/C 全过说明
   鲁棒性结构完整；速度差距是"无行为先验"的样本效率代价。
3. 阶梯对照：先验满速 47m > 纯流形半速 19m > 无 Sonic 失败。

产出：`outputs/token_vae_e27/`、`outputs/isaac_e27_latent/`、
`outputs/isaac_eval_e27.json`。
